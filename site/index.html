How much code can a model see?

Can a small neural network learn to write valid Python?

An ES 335 project by Buha Deep Maheshbhai (24110082).

Two models get the same start of a real test function and finish it, one token at a time. The n-gram counts which tokens followed which in its training code. The MLP is a small neural network. The yellow band is what each model can see while it writes.

Question

Can a small network that sees a fixed window of recent code learn Python’s syntax better than an n-gram that counts token sequences? And does the answer hold on code from repositories that neither model saw during training?

Unit
One Python function. Each function is one row of the dataset.
Target
The next token: a name, a symbol, a line break or an indent.
Known when guessing
Only the tokens before it, and only as many as fit in the model’s window. The rest of the function is not written yet.
The claim covers
How much probability each model gives the real next token, and whether Python’s parser accepts a function the model finished.
Outside the claim
Whether the code runs or does the right thing. Nothing was executed.

Data

The functions come from CodeSearchNet, a public collection of open-source code. Its Python part holds functions from repositories on GitHub.

The dataset is public on Hugging Face, so anyone can download the same pinned version without an account. The downloaded data is not stored in the repository; the first script fetches it and checks its file hashes.

The fields used from each row are the function’s source code, its name, its file path, its repository and the official split it came from. The models read only the code; the repository name decides the split.

The raw data has quality problems. functions are not valid Python 3, some are extremely long, some are copies of each other, and one repository, saltstack/salt, has functions in the official training file alone. Preprocessing deals with each.

Whole repositories are held out, not just functions. Validation and one of the two test sets come from repositories that training never touched, so they show how the models do on projects they have never seen.

Preprocessing

Each choice and its reason. The first four decide which functions are kept, the last three how code becomes tokens.

Drop code that does not parse
It is not valid Python 3, so it would distort the valid-Python measure.
Keep to tokens
Removes trivial and extremely long functions. The upper limit keeps % of the functions that parsed.
Drop near-duplicates
Functions with the same token sequence are copies; keeping them could put the same code in training and test.
At most per repository
So no single project dominates the data.
Remove comments and docstrings
They are natural language, not code, and would inflate the vocabulary.
Strings to <STR>, numbers to <NUM>
Literal values are mostly unique and would otherwise all become <UNK>.
Vocabulary from training only
tokens: every Python keyword and operator, plus the most frequent other training tokens. Test data never shapes it; any other name becomes <UNK>.

Baseline & methods

Both models read code as a list of tokens and give every possible next token a probability. They differ in how much they see, and in how they turn it into a guess.

The n-gram is the baseline. It counts how often each token followed the same short run of tokens in the training code. An order- n-gram looks at the last tokens. When that run never appeared in training, Kneser–Ney smoothing falls back to shorter runs, so no token gets zero probability.

The MLP learns instead of counting. Each visible token becomes a list of numbers, the lists are joined, and one hidden layer of units turns them into a probability for every token in the vocabulary.

Both models assume the next token depends only on a fixed number of tokens before it. The MLP is trained to minimise cross-entropy on the training functions, which is the same quantity perplexity reports.

A longer window also makes a bigger MLP, because only its first layer grows with the context. Each MLP was trained with random seeds.

Perplexity measures how surprised a model is by the real next token. It is how many tokens the model is, in effect, still choosing between: lower is better.

Valid Python is the share of finished completions that Python’s own parser, ast.parse, accepts. Completions that hit the limit of tokens are counted separately.

Every MLP number is a mean over training seeds. The change from seen to unseen repositories comes with a bootstrap interval, made by resampling functions inside each test set.

Full numbers

The same vocabulary, prompts and stopping rule are used for every model. For the validity check each prompt is the first line of a test function plus tokens. A development flag runs the same evaluation code on the validation split instead of the test split.

Errors

Most rejected samples fail on a bracket: one that is never closed, or closed with the wrong kind.

To close a bracket, a model has to know it was opened. Move the window slider: once the window no longer reaches the opening bracket, the model has no way to see it.

Limitations

  • Bigger window, bigger model. The MLP’s first layer grows with its window, so part of the gain from context could come from size.
  • The two test sets differ. The seen-repository test has functions and the unseen one , from different repositories. The bootstrap interval resamples within each set and leaves that difference in place.
  • Parsing is not correctness. Code that Python accepts can still be useless. Nothing was executed.
  • Easier than raw source. Rare names become one unknown token, and strings, numbers, comments and docstrings are removed.
  • Unfinished samples. At temperature the longest-window MLP leaves samples unfinished; the validity rate counts finished samples only.
  • Tuning was limited. Learning rate and hidden size were chosen at one window size with a short training budget.
  • Pooled source files. The official CodeSearchNet files were pooled before my split, and the length cap and near-duplicate filter ran before it too.

Conclusion

Seeing more code helps the MLP far more than the n-gram: on repositories neither saw, the MLP reaches a perplexity of against . The gap is wider for syntax, where of its finished functions parse against .

On new repositories the n-gram loses more than the MLP, and the MLP’s syntax rate barely moves. The claim stops at parsing: none of this code was run.
