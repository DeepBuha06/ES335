Question

Syntax learning and generalization in MLP-based Python code generation

I trained small neural networks to continue Python code, each one able to see a fixed number of previous tokens, and compared them with a classic n-gram model. The question is how much visible code matters for predicting the next token, for writing code that Python accepts, and for code from projects the models never saw.

A function is one row. Each training example is the next token, predicted from a fixed window of earlier tokens and from nothing else. The two scores below answer different questions.

Next-token perplexity

The model is shown the real earlier tokens and scored on the true next token. Lower perplexity means it put more probability on the token that was actually there.

Syntax of a written ending

The model is shown the first line and further tokens, then writes the rest from its own guesses. The headline rate is the share that both finish and parse. The table also divides the valid count by every sample, including ones stopped at the length limit.

At a glance

The tiles show the longest MLP window and the highest-order n-gram. Every context length and n-gram order was fixed before the test run and is listed in the tables below.

1 · How the models work

Writing code one token at a time

Both models read code as a list of tokens (names, symbols, line breaks) and guess the next one. They differ in how much they can see. The n-gram looks up how often the last few tokens were followed by each token in the training code. The MLP turns each visible token into a vector, joins those vectors, and passes them through one hidden layer.

4 · Failure analysis

Why the code breaks: brackets

Most invalid samples fail on a bracket: one that is never closed, or closed with the wrong kind. To close a bracket correctly a model has to know it was opened, and with a short window the opening bracket may already be out of view.

The examples are real samples from the test run that failed on a bracket. The arc joins the opening bracket to the one the parser rejected; the shaded band is what the model could see when it wrote that bracket.

Brackets are the usual way a sample fails to parse. The probability loss sits somewhere else. On unseen repositories the context- MLP still has identifier loss of nats, against for indentation and newlines. Names stay hard after the brackets are mostly right.

5 · Generalization

Code from repositories the models never saw

Whole repositories were held out. On them, perplexity rises for every model except the bigram, and much more for long n-grams: for the order- n-gram against for the context- MLP. Long n-grams rely on exact token sequences that repeat inside one project. The seen-repository functions themselves are held out; other functions from those repositories were used in training.

Syntax carries over almost unchanged: the context- MLP writes valid code for of prompts from seen repositories and from unseen ones.

7 · Method

How the experiment was built

The data

The source is CodeSearchNet's Python functions: functions from repositories, dataset at revision . I pooled the official train, validation, and test files and then made the splits below. The training split still contains functions from the official test file. The reported numbers evaluate this repository split.

Before the split I dropped functions that current Python cannot parse (), functions longer than tokens (that cap keeps percent of functions that parsed), and near-duplicates ( of those groups crossed repositories). I then kept at most functions per repository. Those length and duplicate decisions used the pooled file, including rows that later became test. They were not fit on training rows alone. The vocabulary of tokens was counted on training functions only; every other name becomes one unknown token. Comments, docstrings, and literal values are removed.

The seen-repository test has functions from repositories that also appear in training. The unseen-repository test has functions from repositories absent from training and validation. The two sets differ in size and in which repositories they contain, so the gap between them mixes those differences with the change in perplexity. Validation shares no repository with training.

The models

Both models assign a probability to the next token. The MLP minimizes next-token cross-entropy. The n-gram is interpolated Kneser–Ney smoothing with three discounts per order, fit on training counts only, which lowered the order- validation perplexity from to . The MLP has one hidden layer of units on top of -dimensional token vectors. Learning rate and hidden size were chosen at context and reused. Dropout ( at every context) was chosen on the validation split. Each MLP was trained with seeds. That same validation split also decides when training stops, so validation perplexity is a little kinder than a split that did not choose the settings. The test numbers were not used for those choices.

8 · Evaluation

How the comparison was judged

The grid was fixed before any test number was computed: every n-gram order and every MLP context in the model table, at the temperatures stored with the validity results. Learning rate and hidden size were chosen at context on the validation split and reused. Dropout was chosen on that same split. Early stopping watches it too, so the validation perplexity is a little kinder than it would be on a split that took no part in the choices. The test files were not used for any of those choices. The same vocabulary, prompts, and stopping rule are used for every model. The reported test numbers come from one run of scripts/phase4_eval.py. That script is the only one allowed to open the test files.

Perplexity is the exponential of the mean next-token cross-entropy on the real next token, with the real earlier tokens shown to the model. MLP figures are means over training seeds, and the error bars are the spread of those seeds. The rise from seen to unseen repositories uses a bootstrap interval made by resampling functions inside each set. It does not remove the difference in size between the seen-repository functions and the unseen-repository functions.

Syntax validity in the squares is the share of samples that stopped on their own and that ast.parse accepts. The number table has a second column: valid samples divided by every sample, including ones cut off at the length limit. At temperature the unfinished share is similar across models. At temperature the context- MLP leaves of samples unfinished, against for the order- n-gram.

What these results support

On repositories absent from training, perplexity falls from at context to at context . The order- n-gram levels off at . With the same tokens of context, the MLP at is ahead of the order- n-gram at . The parser check moves further: at temperature , of finished context- completions parse, against for the order- n-gram.

Held-out repositories raise perplexity by for that n-gram and by for that MLP. Exact sequences that repeat inside one project are rare in a new one, and the n-gram depends on them. The syntax rate for the context- MLP stays close: on seen repositories and on unseen ones.

Limits of the claim

A longer MLP window is also a larger model, because the first layer grows with the context. The comparison includes that size difference. The seen-repository test has functions and the unseen-repository test has , drawn from different repositories, so the gap mixes a change of repository with a change of sample size. The bootstrap interval resamples functions inside each set and leaves that design difference in place. A completion the parser accepts can still fail if it is run, and nothing here was executed. Rare names are one unknown token and literals are removed, which makes the sequences easier than raw source. The length cap and the near-duplicate filter were applied to the pooled data before the split; the vocabulary was not.

10 · Reproduction

How to reproduce the page

The data is Hugging Face , Python files, revision . A fresh download is checked against the recorded file hashes. Raw functions stay under data/raw and are left out of the repository. The split uses seed . Commands, timings, and output paths are in the repository README. Result files land in results/ and are copied to site/data. This page reads those files. To open it locally: cd site && python -m http.server 8000. The published copy is the GitHub Pages site.
