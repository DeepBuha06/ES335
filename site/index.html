Syntax learning and generalization in MLP-based Python code generation

I trained small neural networks to continue Python code, each one able to see a fixed number of previous tokens, and compared them with a classic n-gram model. The question is how much the amount of visible code matters for predicting the next token, for writing code that Python accepts, and for code from projects the models never saw.

1 · How the models work

Writing code one token at a time

Both models read code as a list of tokens (names, symbols, line breaks) and guess the next one. They differ in how much they can see. The n-gram looks up how often the last few tokens were followed by each token in the training code. The MLP turns each visible token into a vector and passes them through a small neural network.

4 · Failure analysis

Why the code breaks: brackets

Most invalid samples fail on a bracket: one that is never closed, or closed with the wrong kind. To close a bracket correctly a model has to know it was opened, and with a short window the opening bracket may already be out of view.

The examples are real samples from the test run that failed on a bracket. The arc joins the opening bracket to the one the parser rejected; the shaded band is what the model could see when it wrote that bracket.

5 · Generalization

Code from repositories the models never saw

I held out whole repositories. On them, perplexity rises for every model except the bigram, but much more for long n-grams: for the order- n-gram against for the context- MLP. Long n-grams rely on exact token sequences that repeat inside one project.

7 · Method

How the experiment was built

The data

CodeSearchNet's Python functions: functions from repositories. I removed code that current Python cannot parse ( functions), very long functions and near-duplicates, kept at most functions per repository, and split by repository so that test repositories never appear in training. Comments, docstrings and literal values are removed; the vocabulary keeps the most useful tokens and maps the rest to one unknown-name token.

The models

The n-gram is interpolated Kneser–Ney smoothing with three discounts per order, which lowered the order- validation perplexity from to . The MLP has one hidden layer of units on top of -dimensional token vectors; only the input layer grows with the context, so longer contexts also mean more parameters. Learning rate, hidden size and dropout ( for every context) were chosen on the validation split, and each MLP was trained with three seeds.

Limitations

Valid syntax is not working code, and nothing here was executed. Rare names are one unknown token and literals are removed, which makes the task easier than real code. Longer-context MLPs also have more parameters, so context and model size are not fully separated.
